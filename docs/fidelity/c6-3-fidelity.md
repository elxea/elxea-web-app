## 計測データについて (重要)

`/ja/account/subscriptions` は **ログイン必須 + Shopifyに定期便契約が要る**ため、
確定版の3状態 (契約中 / 一時停止中 / 解約済み) と0件表示を実寸計測できない。そこで
**プレビュー専用の見本契約 (`PREVIEW_SEED=1` / `lib/preview-seed.ts` の
`seedSubscriptionContracts()`)** でFigmaのカードに載っている見本値 (深煎りブレンド
コーヒー豆200g粉/中挽き ¥1,800 / 和紅茶ティーバッグ12個入 標準 ¥2,400 /
次回お届け2026年6月15日 / 1ヶ月ごと・2週間ごと) を流した状態を計測した。

- フラグ未設定時 (= production / Vercel Previewの既定) は `null` を返すので、
  描画は見本導入前とbyte-identical (ログイン誘導のまま)
- Shopifyへは読み書きしない (純粋なオブジェクトリテラル)
- 見本の契約IDは `seed-` 前置きでShopifyの
  `gid://shopify/SubscriptionContract/...` 形式では**ない**。さらに画面側は見本のとき
  `preview` を立てて **Server Actionを1度も呼ばない**ので、見本から実契約へ
  mutationが飛ぶ経路は存在しない (停止・解約・スキップ・頻度変更を押しても
  「プレビュー表示のため、この操作は実行されません。」を出すだけ)
- したがって **Vercel Previewで見えるのはログイン誘導**。3状態と0件表示は上記
  フラグ付きローカルproductionビルドで計測している
- 実ログイン・実契約への操作検証は行っていない (安全制約)

## 12. GID形式検証の対称化 (R で追加・画面計測ではなくサーバ側の契約)

**結論**: 契約IDを取る4つの操作 (停止 / 再開 / 解約 / 次回スキップ) のうち、
**skip だけ**が GID 形式検証を持っていて、停止・再開・解約は素通しだった。
4つとも同じ検証を通るように揃えた。

| 操作 | Server Action | 内部関数 | R 以前の形式検証 | R 以後 |
|---|---|---|---|---|
| 次回をスキップ | `skipNextDeliveryAction` | `skipNextBillingCycle` | あり | あり |
| 一時停止 | `pauseSubscriptionAction` | `pauseSubscription` | **なし** | **あり** |
| 再開 | `activateSubscriptionAction` | `activateSubscription` | **なし** | **あり** |
| 解約 | `cancelSubscriptionAction` | `cancelSubscription` | **なし** | **あり** |
| 頻度変更 | `changeDeliveryFrequencyAction` | (Admin API) | あり + 所有者照合 | 同じ |

商品変更 (`changeSubscriptionProductAction`) は2026-08-12に**削除**した。どのUIからも
呼ばれていない一方で、継続課金額 (`currentPrice`) をクライアント指定のままAdmin APIへ
渡す公開エンドポイントとして生きていたため (所有者照合は通るので他人の契約は触れないが、
自分の契約の金額を任意の値に設定できた)。Admin API側の `changeSubscriptionLineItem` と
`SubscriptionLineInput` も同時に削除し、金額を指定できる経路自体を残していない。

**なぜ必要か (事実)**: `lib/shopify/subscription-actions.ts` の export はすべて
Server Action = 公開HTTPエンドポイントで、`contractId` はクライアント由来。
Customer Account API は「契約が呼び出し元のものか」はトークンでスコープするが、
**id の形が SubscriptionContract かどうかは見ない**。よって
`gid://shopify/Customer/1111` や生の `1111` を渡すとそのまま Shopify へ転送され、
返るエラー文の違いが「どの id が存在するか」を探る手掛かりになりうる。

**どこで弾くか (判断)**: `lib/shopify/customer.ts` の mutation 入口
(`isSubscriptionContractGid` = `/^gid:\/\/shopify\/SubscriptionContract\/\d+$/`)。
Server Action 側ではなくここに置いたのは、Server Action 以外の呼び出し元
(cron / webhook 等) が増えても検証が漏れないため。失敗メッセージは4操作で
**完全に同一** (`Invalid subscription contract ID`) にして、どの操作か・なぜ落ちたかを
漏らさない。

**Admin API 経路との関係**: 頻度変更・商品変更は**ストア全体に効く Admin API
トークン**を使うため、形式検証だけでは足りず `verifySubscriptionContractOwnership`
(同 `customer.ts`) による所有者照合を fail-closed で通す。この2経路は R 以前から
その形なので変えていない。今回揃えたのは「顧客自身のトークンで叩く4操作の形式検証」。

**テストで固定した契約**:

| ファイル | 何を固定したか | 件数 |
|---|---|---|
| `__tests__/subscription-actions-gid-shape.test.ts` (新規) | **Server Action の入口から**呼んで、形式不正な10種の文字列で `fetch` が1度も呼ばれないこと (customer.ts は mock せず実物を通す)。4操作 x 10種 + メッセージ同一性 + 未ログイン + 正常系 | 43 |
| `__tests__/subscription-contract-ownership.test.ts` (追記) | `customer.ts` の4関数が形式不正な8種で Shopify へ出ないこと・4つの失敗メッセージが一致すること・正しいGIDなら従来どおり mutation へ進むこと | +38 |

不正入力の網: 生の数値id / 別リソース種別 (`Customer`) / 数値でないサフィックス /
サフィックス欠落 / 前後の空白 / 余分なセグメント / 負数 / 大文字 GID / 空文字。

**このテストが実際に効いていることの裏取り** (negative control): 修正前の
`lib/shopify/customer.ts` (`2e276bb` 版) に差し替えて同じテストを走らせると
**56件が失敗**する。修正後は3ファイル114件すべて成功。
